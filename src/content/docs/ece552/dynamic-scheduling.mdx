## Static Instruction Scheduling

| Term | Meaning |
| --- | --- |
| **Issue** | The time an instruction begins to execute, i.e. when it is 'issued' into the pipeline |
| **Schedule** | The order in which instructions execute |
| **Scheduling** | Re-arranging instructions to enable rapid issuing |

Scheduling can be done **statically**, i.e. by the compiler. This requires:
- knowledge of pipeline and program dependencies
- a large scheduling instruction scope full of independent instructions

:::tip
Compilers can give themselves a large instruction scope by doing things such as [**loop unrolling**](/ece454/compiler-optimizations/#loop-unrolling).
:::

## Motivation: Dynamic Scheduling

Dynamic scheduling executes instructions in non-sequential order, to:
- reduce [RAW stalls](/ece552/pipelining/#detecting-and-stalling-a-raw)
- increase functional unit (FU) utilization
  - original motivation was for the FP unit, back when that was the largest bottleneck
- expose more opportunities for parallel issue (ILP)

:::caution[Correctness]
It MUST still *appear* as if instructions are executing in order. Otherwise, the scheduling runs the program incorrectly and the CPU is useless.
:::

### Why do it in hardware?

If the compiler can schedule, why build complex hardware for it?

- **Performance portability**: no need to recompile for a new machine
- **More information**: the hardware knows things the compiler cannot possibly know at build time, e.g. memory addresses, branch directions, cache misses
- **More registers**: the hardware can have more physical registers than the ISA exposes to the compiler (via renaming)
- **Easier speculation**: recovering from mis-speculation means flushing, instead of recovery code

:::note[Division of labour]
The compiler has a much larger scope and does as much as it can. Hardware does whatever the compiler could not.
:::

## Instruction Buffer

The instruction buffer is conceptually a bunch of latches for instructions. It gives us our scheduling scope.

Split **D** into two pieces:

| Stage | Job | Order |
| --- | --- | --- |
| **D1** | Accumulates decoded instructions into the buffer | In order |
| **D2** | Sends instructions from the buffer down the rest of the pipeline | *Out of order* |

## Scheduling Algorithm I: Tomasulo

Tomasulo's algorithm has three parts:

| Component | Role |
| --- | --- |
| **Register renaming** | Removes [WAR](/ece552/pipelining/#write-after-read-war-hazards)/[WAW](/ece552/pipelining/#write-after-write-waw-hazards) hazards |
| **Reservation stations (RS)** | The instruction buffer |
| **Common data bus (CDB)** | Broadcasts results to the RS |

:::note
Our example is "Simple Tomasulo": dynamic scheduling for everything, including loads and stores.
:::

## Recall: Dependences

:::tip[Dependence vs. hazard]
Dependences are a property of **programs**. Whether a dependence results in a [hazard](/ece552/pipelining/#dependence-and-hazards)/stall is a property of **pipeline organization**.
:::

[**True (data) dependence**](/ece552/pipelining/#read-after-write-raw-hazards)
- insn *i* produces a result that may be used by insn *j*
- insn *j* is data dependent on insn *k*, and insn *k* is data dependent on insn *i*
- data dependent insns cannot execute simultaneously or be completely overlapped

## Register Renaming

**Idea:** change register names to eliminate [WAR](/ece552/pipelining/#write-after-read-war-hazards)/[WAW](/ece552/pipelining/#write-after-write-waw-hazards) hazards.

> Think of registers (`r1`, `f0`, ...) as **names**, not **storage locations**. So:
> - there can be more locations than names
> - there can be multiple active versions of the same name

### Implementation: the map table

A **map table** maps each name to its most recent location. It is an SRAM indexed by name.

| On a... | Do |
| --- | --- |
| **Write** | Allocate a new location, and note the mapping in the table |
| **Read** | Find the location of the most recent write via a map table lookup |

:::note[Assumption: infinite resources]
Locations must be de-allocated at some point, since resources are finite. For now, assume we have infinite resources.
:::

### Example

- Names: `r1`, `r2`, `r3`, `r4`
- Locations: `p1` to `p8`
- Original mapping: `r1→p1`, `r2→p2`, `r3→p3`, `r4→p4`; `p5` to `p8` are free

<RenameDemo client:visible {...registerRenaming.props} />

:::tip[Takeaway]
Renaming:
- **removes** WAW and WAR dependences
- **leaves RAW dependences intact**
:::

## Tomasulo Organization

The machine splits into an in-order **front end** (fetch, decode/dispatch, register files) and an out-of-order **back end** (reservation stations, functional units, load/store queues). The instruction buffer is implemented by the reservation stations: one set per kind of functional unit (integer, memory, floating point), each with its own issue logic.

<TomasuloOrg {...tomasuloOrganization.props} />

### Data Structures

**Reservation stations (RS#)**
- **FU**, **busy**, **op**
- **Qj, Qk**: source register tags (the RS# of the RS that will produce the input value)
- **Vj, Vk**: source register values

**Map table**
- **T**: tag (RS#) that will write this register

**Common data bus (CDB)**
- Broadcasts `<RS#, value>` of completed instructions

Tags are interpreted as **ready-bits++**:

| Tag | Meaning |
| --- | --- |
| `T == 0` | Value is ready |
| `T != 0` | Value is not ready: watch for the CDB broadcast of `T` |

## New Pipeline Structure

The pipeline is now **F, D, S, X, W**.

| Stage | What happens |
| --- | --- |
| **F** (fetch) | Same as before |
| **D** (dispatch) | **Stall** for a structural hazard (RS full).<br />Input register ready? Read its value into the RS. If not, read its tag into the RS.<br />Set the register status (map table): rename the output register to the allocated RS#. |
| **S** (issue) | **Wait** for RAW hazards and structural hazards (FU busy).<br />Otherwise, read the register values from the RS and send them to execute. |
| **X** (execute) | Same as before. Memory (M) is folded into execute. |
| **W** (writeback) | **Wait** for structural hazards (the CDB).<br />Output register status still matches? Clear the tag and write the result register.<br />The CDB broadcasts to the RS: tag match? Clear the tag, copy the value.<br />Free the RS entry. |

:::note[Stall vs. wait]
A **stall** propagates to younger instructions: nothing behind it can dispatch. A **wait** only holds up that one instruction.
:::

## Value/Copy-Based Register Renaming

Tomasulo-style renaming is called **value-based** or **copy-based**.

- **Names**: architectural registers
- **Storage locations**: the **register file** and the **reservation stations**
  - values can and do exist in both
  - the register file holds the most recent value
  - the RS versions eliminate WAR hazards

Storage locations are referred to internally by **RS# tags**:
- the map table translates names to tags
- tag `0`: the value is in the register file
- tag not `0`: the value is not ready, and is being computed by that RS# (e.g. 4)

The CDB broadcasts values with their tags attached, so instructions know which value they are looking for.

### Value-Based Renaming Example

```
L.S   [r1+0] -> f1
MUL.S f0,f1  -> f2
ADD.S f7,f8  -> f0
L.S   [r1+4] -> f1
```

At dispatch, each instruction allocates an RS. For each input: if it's ready (map tag `0`), **copy the value** into the RS; otherwise **copy the RS#** (tag) into the RS. Then set the map table entry for the output register to the allocated RS#.

<TomasuloSim client:visible {...valueRenaming.props} />

:::tip[What the copies buy]
- `ADD.S` can write `regfile[f0]` before `MUL.S` executes: `MUL.S` already holds its own copy of the old `f0` (no WAR hazard).
- The second `L.S` can write `regfile[f1]` before `MUL.S` executes, and even before the first `L.S` finishes: when the first load broadcasts, `f1` no longer maps to `RS#2`, so the register file isn't touched (no WAW hazard).
:::

## Tomasulo Example

Six instructions on a machine with 3 load buffers, 3 add RS (`Add1` to `Add3`) and 2 multiply/divide RS (`Mult1`, `Mult2`).

| Op | Execute latency (cycles) |
| --- | --- |
| `ADD` (and `SUB`) | 2 |
| `L.S` | 2 |
| `MUL` | 10 |
| `DIV` | 40 |

<TomasuloSim client:visible {...tomasuloExample.props} />

Timing rules the example follows:

- **D**: one instruction per cycle, in program order.
- **S**: as soon as the last operand arrives, even in the same cycle as its CDB broadcast; execution starts the next cycle. In cycle 6, `MUL.S` and `SUB.S` both issue on `Load2`'s broadcast. This assumes their functional units are free.
- **X**: the box holds the cycle execution *finishes*; **W** is the cycle after (if the CDB is free).
- **The register file is written in the first half of the cycle**: `DIV.S` dispatches in cycle 5, the cycle `Load1` writes `f6`, and reads the new value directly.
- An RS entry is freed at W and can be reused from the next cycle.

:::tip[Cycle 58]
**In-order dispatch, out-of-order execution, out-of-order completion.**
:::

## Tomasulo Summary

| Hazard | Tomasulo |
| --- | --- |
| Insn buffer / RS full | **Stall in D** (structural) |
| FU busy | **Wait in S** (structural) |
| RAW | **Wait in S** |
| WAR | None: renaming |
| WAW | None: renaming |

## Dynamic Scheduling as Loop Unrolling

Dynamic scheduling does the three steps of loop unrolling in hardware:

| Step | Effect |
| --- | --- |
| I. Combine iterations | Increases the scheduling scope, for more flexibility |
| II. Pipeline schedule | Reduces the impact of RAW hazards |
| III. Rename registers | Removes the WAR and WAW violations that come from scheduling |

### Loop Example: SAX

SAX (Single-precision A X) is SAXPY without the "PY", only so it fits in the diagrams.

```c
for (i = N; i > 0; i--)
    Z[i] = A * X[i];
```

```
0: L.S   X(r1),f0     // Loop
1: MUL.S f0,f2,f4     // A in f2
2: S.S   f4,Z(r1)
3: SUBI  r1,4,r1      // i in r1
4: BNEZ  r1,Loop
```

Consider two iterations: `L.S, MUL.S, S.S, SUBI, L.S, MUL.S, S.S`. Within an iteration, `L.S -> MUL.S -> S.S` is a RAW chain. Across iterations, the second `L.S` can be hoisted above the first `S.S`, and the two writes of `f0` (and of `f4`) are a WAW that renaming removes.

**Assumptions**
- Multiply takes 4 cycles; `SUBI`, `BNEZ`, a load hit and a store each take 1.
- The 1st load takes 8 cycles (cache miss); the 2nd takes 1 cycle (hit), after the 1st load executes.
- `r1` initially holds 80.
- `&Z[0] == &X[0]`, so each iteration stores to the address it loaded from.
- No speculation: nothing after a branch issues until the branch executes.

<TomasuloSim client:visible {...tomasuloLoop.props} />

:::note
The slides stop at cycle 19 and don't give the 3rd load's latency; the simulator treats it as another miss, so it's still executing at cycle 19 as on the slides. `BNEZ` waits in its own station, `Br1`, which the slides don't draw.
:::

Things to notice:

- **Renaming sets up a dataflow graph.** `MUL.S` waits on `Ld1`, `St1` waits on `Mult1`, regardless of register names.
- **`f0` never gets `Ld1`'s result**, and that's fine: `MUL.S` gets the value directly from `Ld1` over the CDB.
- **The register file is decoupled from computation**, so the 1st and 2nd iterations overlap.
- **Branches** have two options:
  1. No speculation: the branch must resolve before younger instructions can execute. `L.S #2` has its address in cycle 7 but issues in cycle 8, when `BNEZ` executes.
  2. [Speculation](/ece552/speculation/): must have a way to undo [mis-speculation](/ece552/branch-prediction/#speculation) (coming next).
- **Structural hazard, no RS**: in cycle 12, `MUL.S #3` has no free `Mult` station, so it must **stall** in D, which propagates to younger instructions. It dispatches in cycle 17, once `Mult1` is freed.
- **Structural hazard, CDB**: `SUBI #2` finishes in cycle 11 but loses the CDB to the older `L.S #2` in cycle 12, and writes back in cycle 13.
- `S.S` doesn't use the CDB (it has no register result).

### Why can Tomasulo overlap loop iterations?

- **Register renaming**: multiple iterations use different physical destinations for the same registers, i.e. **dynamic loop unrolling**.
- **Reservation stations**: buffer old values of registers, which avoids WAR hazards, and permit out-of-order issue of independent instructions.
- **Other perspective**: Tomasulo builds a **dataflow dependency graph on the fly**.

## Advantages of Tomasulo

1. **Distributed hazard detection logic**: distributed reservation stations and the CDB. If multiple instructions are waiting on a single result, and each has its other operand, they can all issue simultaneously with the broadcast on the CDB.
2. **No stalls for WAW and WAR hazards.**

## Summary

- **Dynamic scheduling** = out-of-order execution
  - higher pipeline/FU utilization, improved performance
  - easier and more effective in hardware than in software: more storage locations than architectural registers, and dynamic handling of cache misses
- **Instruction buffer**: multiple F/D latches
  - implements a large scheduling scope plus "passing"
  - splits decode into in-order **dispatch** and out-of-order **issue** (stall vs. wait)
- **Tomasulo**: copy-based register renaming, fully out of order
