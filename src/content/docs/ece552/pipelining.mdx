## The Sequential Model

This is the model of all modern ISAs.

The **Program Counter (PC)** points to the memory address of the current instruction, and defines the **total order** on dynamic instruction. The next PC is always the next sequential instruction (PC + 4 with 4-byte instructions) unless the instruction says otherwise.

The processor executes a loop:
1. Fetch instruction at the PC
2. Decode the instruction and read the inputs needed to execute instruction
3. Execute the instruction
4. Write the output
5. Increment the program counter

## Single Cycle Processor

<CpuDatapath client:visible {...singleCycle.props} />

| Part | Contains |
| --- | --- |
| **Data path** | Functional units (e.g. the ALU), registers, memory interfaces, etc. |
| **Control path** | Multiplexers, and the control signals for each component, such as write enables |

## Processor Steps

| Stage | What happens |
| --- | --- |
| **Instruction Fetch (F)** | The instruction is fetched from memory at the address indicated by the PC.<br />Increment the PC to point to the next instruction in the sequence. |
| **Decode (D)** | Decode the instruction to find the instruction type (reading the opcode).<br />Decode the required source registers, and read them. |
| **Execution (X)** | The ALU performs an arithmetic/logic operation.<br />For load or store instructions, the ALU often computes the effective memory address.<br />If the instruction is a branch, compute the target PC and update it. |
| **Memory Access (M)** | For a load, fetch the contents of the memory at the computed address.<br />For a store, modify the contents of the memory at the computed address. |
| **Writeback (W)** | Write instruction results to the register file. |

## Multi-Cycle Processor

<CpuDatapath client:visible {...multiCycle.props} />

The multi-cycle processor adds registers to hold temporary data, creating the multi-cycle implementation:

| Register | Holds |
| --- | --- |
| **IR** | The instruction register: the instruction, which is used to determine and drive control signals |
| **A**, **B** | Source register values |
| **O** | The output from the ALU |
| **D** | The output from the memory/data cache |

### Latency and throughput

There is no good way to make a single instruction faster, i.e. decrease its **latency**.

:::tip
We ultimately don't care about latency. We just want programs to go faster. Turns out there are meaningful ways to increase [**throughput**](/ece552/performance/#latency-vs-throughput) in a CPU.
:::

## Pipelining

<ExecTimeline client:visible {...multiVsPipelined.props} />

:::tip
Pipelining improves instruction **throughput** (not latency).
:::

We can think about pipelining by thinking about the multi-cycle design:
- when one instruction flows from stage 1 to stage 2, allow the next instruction to enter stage 1.
- the instruction stages themselves take the same amount of time and the instructions still take the same number of stages

<PipelineDiagram client:visible {...pipelineFlow.props} />

Some instructions may take longer, but **5 instructions are in-flight concurrently**.

## 5 Stage Pipelined Processor

<CpuDatapath client:visible {...pipelinedProcessor.props} />

The temporary values mentioned earlier (PC, IR, A, B, O, D) are now re-latched at every stage in a pipeline register. This is because every single stage of the processor is now executing a different instruction and will need different values.

There are latches (**pipeline registers**) in between each stage, named by the stages they separate: `PC`, `F/D`, `D/X`, `X/M`, `M/W`.

## Terminology

| Term | Meaning |
| --- | --- |
| **Scalar pipeline** | One instruction per stage, unlike a **super-scalar** pipeline, where one stage might execute more than one instruction |
| **In-order pipeline** | Instructions are fed through the pipeline to execute in program order |
| **Pipeline depth** | The number of pipeline stages |

## Instruction Conventions

Some ISAs put the instruction destinations on the left, for example:
```asm
add r1, r2, r3 # r1 <- r2 + r3
```
and some on the right:
```asm
add r1, r2, r3 # r1 + r2 -> r3
```

:::note[Course convention]
In this course, examples use `add r2, r3 -> r1` to be explicit and make the destination register clear.
:::

## Pipelining Principles

| Principle | Meaning |
| --- | --- |
| **Balance** | All stages should take approximately the same time. It doesn't make sense to optimize any stage that is not the longest.<br />Instructions must pass through all stages in the same order, even if the stage is not needed. |
| **Buffering** | Not all stages take the same time, so instructions will sit and wait until the next stage is ready to accept them. |
| **Independent computations** | No relationships between work units, to minimize pipeline stalls. |

## Pipelining Performance

Let's say you have a CPU which has the following instruction distribution:
- 20% branch
- 20% load
- 60% ALU

Here is what that looks like in terms of performance, where

$$
\text{performance} = \text{clock period} \times \text{CPI} \quad (\text{time per instruction})
$$

| Design | Clock period | CPI | Performance |
| --- | --- | --- | --- |
| Single-cycle | 50 ns | 1 | 50 ns/instr |
| Multi-cycle | 11 ns | 4 | 44 ns/instr |
| Pipelined | 12 ns | 1 | 12 ns/instr |
| Pipelined, with stall penalties | 12 ns | 1.5 | 18 ns/instr |

**Multi-cycle:** branch takes 3 cycles, load 5 cycles, ALU 4 cycles, so

$$
\text{CPI} = 0.2(3) + 0.2(5) + 0.6(4) = 0.6 + 1.0 + 2.4 = 4
$$

$$
\text{performance} = 11\ \text{ns} \times 4 = 44\ \text{ns/instr}
$$

**Pipelined:** the clock period is the single-cycle delay split over 5 stages, plus overhead:

$$
\text{clock period} = \frac{50\ \text{ns}}{5\ \text{stages}} + \text{overhead} = 12\ \text{ns}
$$

[CPI](/ece552/performance/#cycles-per-instruction-cpi) = 1: each instruction takes 5 cycles, **but** 1 instruction completes every cycle, so performance is 12 ns/instr. Actually, CPI = 1 + some penalty for pipelining; say CPI = 1.5, giving $12 \times 1.5 = 18$ ns/instr.

**Why is the pipeline clock period greater than (delay through datapath) / (# of pipeline stages)?**
- pipeline registers add delay
- pipeline stages themselves have different delays: the clock period must account for the longest stage
- extra bypass logic

These factors have implications for the ideal number of pipeline stages.

**Why is pipeline CPI greater than 1?**
- CPI for a scalar in-order pipeline will be 1 + stall penalties
- Stalls are used to remove hazards

| Term | Meaning |
| --- | --- |
| **Hazard** | A condition that jeopardizes the sequential illusion |
| **Stall** | A pipeline delay introduced to restore the sequential illusion |

### Calculating pipeline CPI

Each kind of stall adds (frequency of the stall) $\times$ (stall cycles). The penalties simply add, since stalls generally don't overlap in in-order pipelines:

$$
\text{CPI} = 1 + \text{stall-freq}_1 \times \text{stall-cyc}_1 + \text{stall-freq}_2 \times \text{stall-cyc}_2 + \dots
$$

:::tip[Make the common case fast (MCCF)]
Long penalties are OK if they happen rarely, e.g. a 10-cycle stall on 1% of instructions: $1 + 0.01 \times 10 = 1.1$.

Stalls also have implications for the ideal number of pipeline stages.
:::

## Pipeline Management

Proper pipeline management requires two **pipeline operations**. These are achieved using control signals: the pipeline registers' write-enable and clear signals.

| Operation | What it does | Implementation |
| --- | --- | --- |
| **Stall** | Stop an instruction in its current stage. Younger instructions must wait for the older instructions to complete. | De-assert the write enables of the pipeline registers |
| **Flush** | Remove an instruction from the current stage. Used for [control hazards](/ece552/branch-prediction/#control-hazards). | Assert the clear signals |

:::caution
Both **stalls** and **flushes** must also propagate to all younger instructions.
:::

## Dependence and Hazards

| | Dependence | Hazard |
| --- | --- | --- |
| **What it is** | A relationship that serializes two instructions | The possibility of the hardware executing instructions incorrectly (such as by using the wrong data) due to pipelining. Another way to think about a hazard is breaking the sequential illusion. |
| **A property of** | The program, not the hardware | The hardware |

There are two kinds of dependence:
- **Data dependence:** two instructions use the same value or storage.
- **Control dependence:** one instruction affects whether another instruction executes or not.

Hazards can be fixed by **stalling**: the instruction stays in the same stage for multiple cycles.

## Read-after-write (RAW) Hazards

Take the following instructions:
```asm
add r2, r3 -> r1
sub r1, r4 -> r2
or r6, r3 -> r1
```

The `sub` instruction absolutely requires that the `add` instruction completes and writes to the `r1` register first. If we swapped the `add` and the `sub`, the `sub` would use the wrong value.

A **true dependence** is one where the actual data is depended on. Using a different register doesn't solve this.

Imagine these instructions:
```asm
add r1, r2 -> r3
lw #0(r3) -> r4
addi r3, #1 -> r6
sw r3 -> #0(r7)
```

The `add` instruction is writing to `r3`, which is needed by the next three instructions. How would this flow through a pipeline?

<PipelineSim client:visible {...rawSim.props} />

As you can see in the animation above, the `lw` and `addi` instructions read the wrong value, because the `add` instruction has not finished writing to the register file in time for them to read it. The `sw` reads `r3` in the same cycle the `add` writes it, so it gets the right value (see internal forwarding below).

Independent operations, like `add r1, r2 -> r3` followed by `add r4, r5 -> r6`, share no registers and flow through the pipeline without any problem.

### Internal Forwarding

In cases where we have **internal forwarding**, we assume that the **W** stage of the pipeline writes to the regfile in the first half of the cycle, and the **D** stage reads in the second half. This means that we can read a value that is being written to the regfile in the same cycle.

:::note
We will generally assume this to be true unless told otherwise.
:::

### Detecting and stalling a RAW

**Stall logic** detects the hazard and stalls the reader in D. It stalls while either source of the instruction in D is the destination of an instruction in X or M:

```
(F/D.rs1 && (F/D.rs1 == D/X.rd || F/D.rs1 == X/M.rd)) ||
(F/D.rs2 && (F/D.rs2 == D/X.rd || F/D.rs2 == X/M.rd))
```

The condition is re-evaluated every cycle until it is no longer true. While it holds, the hazard logic de-asserts the write enables of the PC and F/D registers (so F and D hold their instructions) and inserts a nop into D/X.

| | |
| --- | --- |
| **+** | Low cost, simple |
| **−** | IPC degradation: RAW dependences are common |

In a pipeline diagram, we will denote a stall by writing `d*` for a data stall, and `p*` for a propagated stall.

<PipelineDiagram client:visible {...rawStallDiagram.props} />

Notice something about the stall here:
- `lw` already gets r3 from the regfile
- but `add` hasn't yet written r3 to the regfile (hence stall)

But does this **need** to happen? Even though `lw` has to wait for r3 to be written, it hasn't actually used it yet. And the `add` has actually *already produced* the value that would be written to r3 in the pipeline. It just hasn't been written to the register file yet.

**But if it has already been produced, can we just give it straight to the `lw` before writing to the regfile so the `lw` doesn't have to wait?**

Yes, **bypassing**.

### Bypassing (Forwarding) RAW Stalls

The data being written must be written to the register file. But there is no need for other instructions to wait for that to happen to use the data.

**Bypassing** is reading a value from an intermediate source before it is written to the primary source.

| Bypass | From | To |
| --- | --- | --- |
| **MX** | The beginning of the M phase, i.e. the output of the X/M pipeline register | The ALU input muxes in the X phase |
| **WX** | The beginning of the W phase, i.e. the output of the M/W pipeline register | The ALU input muxes in the X phase |
| **WM** | The beginning of the W phase, i.e. the output of the M/W pipeline register | The data input mux in the M phase |

<BypassPaths client:visible {...bypassPaths.props} />

**Bypass logic** is similar to, but separate from, the stall logic:
- Stall logic controls the pipeline registers (latches); bypass logic controls the mux inputs.
- They complement one another: if you can't bypass, you must stall.

For example, the mux in front of ALU input A picks its source like this:

| Condition | Mux input |
| --- | --- |
| `X/M.rd == D/X.rs1` | 0: MX bypass |
| `M/W.rd == D/X.rs1` | 1: WX bypass |
| otherwise | 2: the register file value |

#### Load-Use Hazards

Load-use hazards must receive special consideration. They are still RAW hazards. But unlike other RAWs, the data is *not* available after the X phase as it does not come from the ALU. The data comes from memory, and gets latched in the M/W pipeline register. This means an MX bypass is **insufficient**, and you need a WX bypass.

Whether a stall is needed depends on *where* the instruction directly after the load uses the loaded value. The value only exists at the end of M, so it can first be bypassed at the start of the load's W:

| Use of the loaded value | Example | Result |
| --- | --- | --- |
| **In X** (an ALU input or an address) | `sub r1, r4 -> r2` | A **1-cycle stall is unavoidable**: X starts while the load is still in M. The WX bypass keeps it to 1 stall; without it, the use waits for the register file write, which costs **2 stalls**. |
| **In M** (the data of a store) | `sw r1 -> #0(r4)` | **No stall:** the WM bypass delivers the value at the start of the store's M, just in time (see the WM example above). |

:::caution
Since W comes one cycle after M, a load-use stall cannot be avoided when the use is in X. Only a load-store pair, where the value is needed in M, avoids the stall completely, using the WM bypass.
:::

Here is a pipeline diagram for:
```asm
lw #4(r3) -> r1
sub r1, r4 -> r2
```

<PipelineDiagram client:visible {...loadUseDiagram.props} />

Without a WX bypass, the same pair costs 2 stall cycles, since `sub` has to wait until it can read `r1` from the register file in cycle 5:

<PipelineDiagram client:visible {...loadUseNoWxDiagram.props} />

Additionally, observe how using an MX bypass for a load-use RAW hazard would incorrectly use the effective address instead of the data from the data cache/memory.

<PipelineSim client:visible {...loadUseSim.props} />

So even with full bypassing, stall logic is unavoidable. The load-use stall condition, checked while the load is in X and its user is in D:

```
Stall = (D/X.op == LW) &&
        ((F/D.rs1 == D/X.rd) || (F/D.rs2 == D/X.rd && F/D.op != SW))
```

A store's `rs2` is its data, which is only needed in M, so the WM bypass covers it without a stall.

#### Performance impact of the load-use penalty

Assume branches are 20% of instructions, loads 20%, stores 10% and other 50%, and 50% of loads are followed by a dependent instruction that needs a 1-cycle stall (the insertion of 1 nop):

$$
\text{CPI} = 1 + (1 \times 0.2 \times 0.5) = 1.1
$$

## Write-after-write (WAW) Hazards

Take the following instructions:
```asm
add r2, r3 -> r1
sub r1, r4 -> r2
or r3, r6 -> r1
```

There is a potential write after write hazard on `r1` between the `add` and the `or`.

For the compiler, this is a scheduling problem: reordering the `add` and the `or` would leave the wrong value in `r1`.

These dependences are [**artificial**](/ece552/dynamic-scheduling/#register-renaming) (i.e. no value flows through the dependence): we could simply just replace the `r1` in the `or` with another register, e.g. `r8`.

WAW hazards **do not affect** in-order pipelines where every instruction spends exactly one cycle in X, because instructions cannot 'leapfrog' each other in the pipeline: they will all reach the write phase in order. They **can** happen with multi-cycle operations, which spend multiple cycles in execute (see Handling WAW Hazards below).

## Write-after-read (WAR) Hazards

```asm
add r3, r2 -> r1
sub r4, r5 -> r2
or r1, r3 -> r6
```

The `sub` writes `r2`, which the older `add` reads. For the compiler, this is a scheduling problem: reordering them would make the `add` use the wrong value.

Similar to the WAW hazards, this is an [artificial dependence](/ece552/dynamic-scheduling/#register-renaming) which can be resolved by replacing the register used: use a different output register for the `sub`, e.g. `r8`.

Also, WAR hazards **do not affect** this simple in-order pipeline. They can happen with out-of-order execution.

## Data Hazards: Summary

Real instruction sequences pass values via registers and memory. There are three kinds of data dependences:

| Read-after-write (RAW) | Write-after-read (WAR) | Write-after-write (WAW) |
| --- | --- | --- |
| **True dependence** | **Anti-dependence** | **Output dependence** |
| `add r2, r3 -> r1`<br />`sub r1, r4 -> r2` | `add r2, r3 -> r1`<br />`sub r5, r4 -> r2` | `add r2, r3 -> r1`<br />`or r6, r3 -> r1` |

- Where's the fourth? There is no read-after-read dependence: reading a value twice doesn't serialize anything.
- There is only one dependence between any two instructions (RAW has priority).
- A dependence is a property of the program and the ISA.

**Data hazards** are a function of the data dependences *and* the pipeline:
- They are the potential for executing dependent instructions in the wrong order.
- They require both instructions to be in the pipeline ("in flight") at the same time.

## Pipelined Functional Units

The pipeline we have looked at so far is shallow and simple. Real pipelines are much deeper.

For example, the execute stage itself is usually a deep pipeline with many stages in real CPUs. Each stage can be decomposed into several stages. Looking at X:

| Operations | Latency |
| --- | --- |
| Fast integer arithmetic and logic | 1 cycle |
| Slow integer arithmetic: multiply, divide | Pipelined across multiple cycles |
| Floating point add, multiply | Pipelined |
| Floating point divide, square root | Multiple cycles, but not pipelined |

<FuPipelines client:visible {...fuPipelines.props} />

How many stages does a unit have, and what is the minimum number of cycles between independent instructions of the same type (no RAW dependency)? For example, in the Intel Pentium Pro:

| Unit | Stages | New instruction every |
| --- | --- | --- |
| Integer multiply | 4 | cycle |
| FP add | 3 | cycle |
| FP multiply | 5 | 2 cycles |

### Hazards with multi-cycle operations

| Hazard | With long operations |
| --- | --- |
| **RAW** | Stalls are more frequent |
| **WAW** | Now possible: instructions no longer reach W in order |
| **WAR** | Still not possible: registers are always read in D |

### Handling WAW Hazards

Below, the `ADD.S` finishes before the older `DIV.S`, so `f2` ends up holding the `DIV.S` result, and the later reader of `f2` gets the wrong value.

<ControlHazardPipeline client:visible {...wawHazard.props} />

| Option | | |
| --- | --- | --- |
| **I: Stall the younger instruction (`ADD.S`) at W** | Simple, intuitive | Lower performance, cascading stalls |
| **II: Cancel the older instruction's (`DIV.S`) writeback** | No performance loss | Complex: what if an instruction in between (e.g. a `S.S` that reads the `DIV.S` result) causes an exception? |

## Structural Hazards

A **structural hazard** is when a resource is needed twice in one cycle. For example, multiple writebacks in one cycle, or a shared instruction/data cache.

<ControlHazardPipeline client:visible {...structuralHazard.props} />

Structural hazards can be fixed by **stalling**: add stall logic to stall the pipeline when the hazard occurs. Structural stalls are written `s*`.

**Which one should stall, the `lw` or the `and`?** Stall the younger instruction (the `and`):

| | |
| --- | --- |
| **+** | Low cost, simple |
| **−** | Increases CPI |

:::tip[Avoid structural hazards by design]
The best fix is proper ISA/pipeline design: each instruction uses every structure exactly once, for at most one cycle, and always in the same stage relative to F.
:::
